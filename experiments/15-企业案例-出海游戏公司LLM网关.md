### 3.2 数据流（AI NPC 对话为例）

```
玩家发话 ("帮我找下任务点")
   │ (1) WebSocket → 阿里云全球加速
   ▼
[Edge Gateway 新加坡节点]
   │ (2) JWT 认证 + QPS 检查
   ▼
[Layer 4-2 语义缓存]
   │ (3) 查相似问题（命中率 35%）
   │      命中 → 直接返回（10ms）
   │      未命中 ↓
   ▼
[Layer 4-1 智能路由 - 三档分层]
   │ (4) 判断对话复杂度（基于 prompt 长度 + 任务类型）
   │     简单 NPC 对话(70%)  → 910C-台1 跑 V4-Flash
   │     复杂 RAG/客服(25%) → 910C-台2 跑 V4-Pro INT8
   │     极复杂推理(5%)     → 云端 V4 满血 API 兜底
   ▼
[Layer 4-3 玩家上下文]
   │ (5) 拉 Redis 最近 5 轮对话 + ChromaDB NPC 长期记忆
   ▼
[Layer 3-1 本地 MindIE 推理 (Ascend 910C)]
   │ (6) V4-Flash 或 V4-Pro 推理 + 流式生成
   │     Flash 首 token < 250ms / Pro 首 token < 600ms
   │     都通过 910C HBM 3.2TB/s 优势加速
   ▼
[Layer 4-4 输出审核]
   │ (7) 黑名单 + 政治敏感词过滤
   ▼
返回玩家（首字符 500ms，全文 1.5s）
```

## 5. 关键技术细节（深挖 4 个）

### 5.1 AI NPC 的"人格一致性"问题

**痛点**：NPC 张三在第 1 章说自己讨厌喝酒，第 5 章玩家请客时回答"好啊我最爱喝酒"——人设崩塌。

**根因**：纯 prompt 工程做不到，因为单次对话 context 装不下 NPC 全部历史。

**方案**：**RAG + Memory 双层架构**

```
NPC "张三" 的记忆系统:
├── 静态人格库 (RAG 知识库)
│   · 出身/性格/口头禅/亲属关系/价值观（500条事实）
│   · 由游戏策划在编辑器里维护
└── 动态记忆 (ChromaDB)
    · 与玩家 X 的历史对话（自动入库）
    · 关键事件标记（"答应过玩家 X 帮忙找剑"）
    · 衰减策略：30 天未触发的记忆降权
```

**每次对话**：
1. 检索 NPC 张三的静态人格（top-10 事实）
2. 检索张三与当前玩家的 top-5 历史互动
3. 拼接到 system prompt，再让 LLM 回答

**实测**：人格一致性测试集 100 题，纯 prompt = 62 分，RAG+Memory = 89 分。

**MindIE 部署关键参数**（生产实测）

**V4-Flash 集群（台 1）**：
- 量化：FP16 不量化（70B 模型 140GB / 512GB 显存绰绰有余）
- 单 910C 卡 batch size = 32，KV cache 占用 14GB
- 首 token < 250ms，单卡稳定 150 QPS，整机 1200 QPS

**V4-Pro 集群（台 2）**：
- 量化：W8A8 INT8（235B 模型 235GB / 512GB 显存）
- 单 910C 卡 batch size = 8，KV cache 占用 25GB
- 首 token < 600ms，单卡稳定 80 QPS，整机 640 QPS
- INT8 精度损失 < 1%（DeepSeek 官方量化方案）

**智能路由决策树**（生产规则）：
```python
# Layer 4-1 路由逻辑（伪代码）
def route(request):
    prompt_len = len(request.prompt)
    task_type = classify(request)
    
    # 极复杂任务走云端兜底
    if task_type in ["数学推理", "代码生成", "长文档分析"]:
        return "云端 V4 满血"
    
    # 中等复杂走 Pro
    if prompt_len > 4000 or task_type in ["RAG 客服", "多轮剧情"]:
        return "910C-Pro INT8"
    
    # 默认走 Flash 快路径
    return "910C-Flash FP16"
```

### 5.2 语义缓存——降本核心

游戏里 NPC 问题高度重复：
- "你好" / "Hello" / "Hi 张三" — 同一类问题
- "我的任务在哪" / "下个任务点" / "Where is my quest" — 同一意图

**做法**：
1. 玩家输入 → Embedding（text-embedding-v2，1536 维）
2. ChromaDB 余弦相似度搜索
3. 阈值 > 0.92 → 命中缓存，直接返回
4. 命中率实测 **35%**

**成本影响**（基于三档分层加权成本 ¥0.05/M）：
- 不开缓存：5000 QPS × 86400s × 30 天 × 200 tokens × ¥0.05/M = ¥130 万/月
- 开缓存：65% × ¥130 万 = ¥84 万/月
- **每月省 ¥46 万**

**三档分层 vs 纯满血云端方案的成本对比**：
| 方案 | 加权 Token 成本 | 月成本（开缓存）|

| 纯满血 V4 云端 API | ¥0.50/M | ¥845 万/月 |

### 5.3 多语言聊天审核（最复杂的一环）

**挑战**：5 国语言（印尼/越南/泰国/阿拉伯/韩语）+ 方言 + 火星文绕过

**架构**：
```
聊天消息
   ↓
[BM25 黑名单] (50ms)
   - 已知违禁词命中 → 拒绝
   - 模糊词进入下一层
   ↓
[语言识别] (20ms)
   - fasttext lang-id
   ↓
[百炼内容安全 API] (200ms)
   - 多语言违禁内容检测
   - 高置信(>0.9) → 自动判定
   ↓
[本地 LLM 上下文判断] (500ms)
   - 模糊场景：辱骂 vs 调侃
   - Qwen2.5-7B + 游戏黑话词典 RAG
   ↓
[人工复审队列] (申诉)
```

**关键创新**：**游戏黑话词典 RAG**——把"挂、外挂、G、玻璃心、傻 X(空格变体)"等游戏圈违禁词单独建库，**误判率从 18%（通用模型）降到 4%**。

**DeepSeek-V4-Flash 在审核场景的优势**：
- 中文 + 阿语 + 印尼语混合识别能力强（训练语料 30% 多语言）
- MoE 路由对"语言识别 → 内容判断"任务有天然解耦
- 长上下文 128K 装得下整个游戏黑话词典作为 in-context 示例

### 5.4 本地化翻译——出海最痛

**老流程（6 周）**：
1. 策划写中文 → 翻译公司报价 → 译稿回收 → QA 校对 → 嵌入资源 → 测试

**新流程（5 天）**：
1. 策划在 CMS 标记"待翻译"
2. **Qwen-MT + 游戏术语库 RAG**自动批量翻译
3. 本地 7B 模型做风格统一（保持 NPC 语气）
4. 翻译公司**只校对**而非翻译，工作量降 80%
5. CI/CD 自动嵌入资源 + 出包

**成果**：
- 单次本地化成本：¥30 万 → ¥6 万（-80%）
- 周期：6 周 → 5 天
- 8 国语言一次完成

## 9. 🎯 项目经验总结（面试讲故事的核心）

### 9.1 8 条可复用的 SA 方法论

**1. "AI 不是一个延迟需求，是多个延迟需求"**
> 游戏里 NPC（<1s）、审核（<500ms）、客服（<3s）、翻译（离线）需求完全不同。**SA 第一件事是分场景做 SLA 矩阵**，再分别选型，**不要试图用一个统一架构解决所有问题**。

**2. "本地 + 云端混合是 ROI 最高的方案"**
> 90% 流量本地 GPU 解决成本和延迟问题，10% 流量云端解决弹性和长尾问题。**纯本地浪费弹性，纯云端浪费成本**。

**3. "客户最初的需求往往是错的"**
> 客户要买 H100，我说服换 Ascend 910C，省 ¥210 万 + 解决制裁风险；客户要做"超大稠密模型 NPC"，我建议用 MoE 架构（DeepSeek-V4-Flash），**激活参数小推理快**。**SA 的价值是帮客户做更好的选择，不是满足错误的需求**。

**4. "国产化不是政治正确，是商业账"** ⭐ 国产化方案新增
> 三笔账必须给客户算清：
> - **硬件账**：910C 单卡价是 H100 的 1/4，同等预算 4 倍算力
> - **合规账**：进中东/俄罗斯/非洲市场，国产化是入场券
> - **生态账**：DeepSeek-V4-Flash 在 CANN 上有官方优化，**性能反而比 H100 + vLLM 快 15%**
> 国产化的代价是**软件栈不成熟 + 人才稀缺**——这正好是阿里云专家服务的机会。

**5. "A/B 测试是 AI 落地的必经之路"**
> AI 上线**必须配对照组**，不然客户老板永远问你"提升从哪来的"。我们在试点阶段强制做了 A/B，**结果不仅证明了价值，还反向找到了 3 个需要优化的场景**。

**6. "运维交接比技术方案更重要"**
> 客户 SRE 团队接不住 LLM 系统是 90% 案例失败的原因。国产化方案尤其严重——**Ascend 软件栈人才市场上几乎没有**。我们配套设计了**托管运维包 + 3 个月伴飞**——这是阿里云的高毛利服务收入，也是客户成功的保障。

**7. "DeepSeek V4 三档分层是国产化 SA 的黄金工具"** ⭐ V4 三档版新增
> 不要陷入"哪个模型最好"的争论，正确思路是**按流量分级**：
> - 70% 简单流量 → V4-Flash 本地（成本 ¥0.015/M）
> - 25% 中等流量 → V4-Pro 本地 INT8（成本 ¥0.060/M）
> - 5% 极复杂流量 → V4 满血云端 API（成本 ¥0.50/M）
>
> **加权成本 ¥0.05/M = 纯满血方案的 1/10**，同时复杂任务质量不打折。
> 关键认知：**V4-Pro 是为 910C×8 INT8 量身定做（235GB 刚好装下 512GB）**——这是 DeepSeek 团队的精确瞄准，SA 必须用好。

**8. "SA 的 KPI 不是单期收入，是客户 LTV"** ⭐ 国产化方案新增
> 这次因为客户自购 GPU，阿里云**少卖了 ¥150 万/年 GPU 租赁**。但赢得了：
> - 客户后续 4 款新游戏全部走阿里云架构（3 年 LTV ¥2000 万+）
> - 一个**国产化标杆案例**，可以复制到其他出海客户
> - 阿里云在"国产化方案"上的认知度提升
> **真正的 SA 不算单笔账，算 3 年账**。
