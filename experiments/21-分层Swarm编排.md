# 实验 #21: 分层 Swarm 编排（顶层规则路由 + 嵌套子 orchestrator）

> **核心结论**: 把已有 5 个实验（#06 DAG / #12 回路 / #18 缓存 / #20 路由 / 单 agent）组装成一个
> **顶层规则路由 + 按子任务结构分发到不同 orchestrator** 的分层系统。**四臂对照 + 剥离实验**（9 条异构请求）真实数据：
> **分层混合 C 准确率 0.889、总 LLM 调用 18，对"全程 Reflection" B（0.667 / 63 调用）形成帕累托占优——准确率更高、成本仅 1/3.5。**
> 剥离实验把 C 相对单 agent A 的 +0.445 准确率拆成两块：**纯架构 +0.112（路由本身）+ 云端容量 +0.333（把难题送上云端）**。
> 三个发现：① **C 帕累托占优 B**（既准又省，是稳健结论，不受单轮噪声影响）；
> ② **架构与算力都有功劳，但本轮云端容量贡献更大**——架构的真正价值是"知道在哪儿花云端的钱"（C/D 调用数相近，但 C 把钱精准砸在难题上）；
> ③ 小样本 + 本地模型非确定性导致 B 在两轮间 0.444→0.667 漂移，**单轮数字不可尽信，只有帕累托占优这类强结论稳**。

## 1. 假设与动机

前几个实验各自证明了一种 orchestrator，但生产系统的真问题是：**异构请求该用哪种?**
教材常暗示"用最强的(Reflection/多 agent)兜底最稳"。本实验用三臂对照证伪这个直觉，
并验证 **"按需分配算力"**：顶层用最便宜的路由分流，只在真正复杂的分支才动用昂贵 orchestrator。

**待验证假设**:
- H1: 分层 C 的准确率 ≥ "全程单 agent" A（路由把难题送到更强 orchestrator）
- H2: 分层 C 的总 LLM 调用（成本代理）≈ A，远小于"全程 Reflection" B（简单请求走廉价路径）
- H3: 规则路由能覆盖大多数高频意图，LLM 兜底只接少量难例

## 2. 架构

[hierarchical_swarm.py](hierarchical_swarm.py)，子 orchestrator 全部复用，零重写：

```
请求 ──► L0 规则路由(零 LLM, 正则) ──┬─ faq    ─► 缓存直返(0 LLM)          #18
                                    ├─ billing─► 单 agent run_agent(本地)
                                    ├─ tech   ─► Plan-Execute DAG(云端)   #06
                                    ├─ policy ─► Reflection 回路(云端)     #12
                                    └─ miss   ─► L0b LLM 路由兜底(云端)─►再分发 #20
```

**Provider 混合策略（贴近生产）**：简单意图(faq/billing) 走本地 1.5B（免费/快），
复杂意图(tech/policy) 走云端 qwen-turbo（能力强）。这正是 hybrid 路由的意义：**钱花在刀刃上**。

| 子 orchestrator | 选它的依据（机制） | 复用 |
|---|---|---|
| 缓存直返 | 无依赖无推理 → 别动 agent | #18 |
| 单 agent | 单步结构化 → 一次调用够 | run_agent |
| Plan-Execute DAG | 多步有依赖/分支 → 状态机 | #06 |
| Reflection 回路 | 要改到达标 → 必须带环 | #12 |
| LLM 路由兜底 | 规则不可枚举 → 才上 LLM | #20 |

## 3. 四臂对照 + 剥离实验（9 条异构请求，5 类意图）

度量口径：**主指标 = LLM 调用次数（provider 无关、完全公平的成本代理）**；
准确率 = 答案命中预设关键词（粗粒度但各臂一致、可比）；延迟标注 provider 构成。
**D 臂是剥离对照**：与 C 完全相同的分层路由决策，但所有子 orchestrator 强制走本地 1.5B
——用来把"架构功劳"和"云端容量功劳"分开。

| 臂 | 准确率 | 总 LLM 调用 | 均延迟 | provider | 角色 |
|---|---|---|---|---|---|
| **A 全程单 agent** | 0.444 | 17 | 3017 ms | 本地 1.5B | 最便宜基线 |
| **B 全程 Reflection** | 0.667 | **63** | 10567 ms | 本地 1.5B | 全程最强 |
| **D 分层（全本地）** | 0.556 | 25 | 5937 ms | 本地 1.5B | 剥离：纯架构 |
| **C 分层（混合）** | **0.889** | **18** | 5075 ms | 混合 | 架构 + 选择性云端 |

C 的规则路由命中率 **0.889（8/9 走规则，1 条 miss 触发 LLM 兜底）**。

### 功劳拆解（剥离实验核心）

```
C 相对 A 的总收益 = +0.445
├─ 纯架构 (D − A) = 0.556 − 0.444 = +0.112   ← 路由本身（faq 直返 + 送对 orchestrator）
└─ 云端容量 (C − D) = 0.889 − 0.556 = +0.333  ← 把难题送上 qwen-turbo
```

**关键观察（比上一版更诚实）**：

**① 最稳健的结论——C 帕累托占优 B（既准又省）**
C 0.889 / 18 调用 vs B 0.667 / 63 调用：**准确率更高、成本只有 1/3.5、延迟少一半**。
这是不依赖单轮噪声的强结论——无论分项怎么抖，"分层混合"在准确率和成本两个维度同时压过"全程最强"。

**② 架构和算力都有功劳，但本轮云端容量贡献更大（修正上一版"架构 > 算力"的过度断言）**
剥离显示纯架构只 +0.112，云端容量 +0.333。**所以不能说"架构 > 单点算力"。**
更准确的说法：**架构的价值是"知道在哪儿花云端的钱"**——D 和 C 调用数相近（25 vs 18），
但 C 把这些调用精准投在 tech/policy 难题上，于是同样的预算量级换来高得多的准确率。架构决定算力的投放效率。

**③ "全程最强"不是一无是处，但永远被分层支配**
本轮 B（0.667）确实超过单 agent A（0.444）——Reflection 这轮起了作用（与上一轮 0.444 不同，见局限③）。
但 B 要烧 63 次调用、10.5s 延迟，**仍被 C 在准确率上反超**。结论不是"Reflection 没用"，而是
**"全程开 Reflection 是把它用错地方"**：它该被路由层只派给真正需要迭代的子任务（C 里 policy 才用回路）。

**④ 工程发现：worker 失败必须隔离（踩坑实录）**
本实验第一次跑时，本地 1.5B 的 planner 偶发输出缺 `purpose` 键 → `run_plan_execute_agent` 抛 `KeyError`
→ 整轮实验崩溃。修法两步：① runner 给每条 query 包 try/except（单条失败记 0 分继续，不拖垮全局）；
② 修 `agent.py::build_executor_prompt` 用 `.get()` 防御缺键。**这正是报告生产清单里"worker 失败隔离"那条的真实注脚**——
swarm 规模一大，子 orchestrator 的非确定性崩溃是常态，必须在调度层兜住。

## 4. 诚实的局限与混淆项

1. **样本量小（9 条）+ 本地模型非确定性 → 单轮数字会抖**：两轮间 B 从 0.444 跳到 0.667、D 是新增臂。
   只有"C 帕累托占优 B"这类跨维度强结论稳，分项准确率不能下统计结论（对齐 #19 对显著性的严谨）。
2. **剥离不完美**：D 臂在那 1 条规则 miss 上，LLM 兜底路由仍走了云端（1 次 cloud 分类调用），
   非 100% 纯本地；但 dispatch（真正干活的部分）已全本地，不影响功劳拆解的主结论。
3. **规则路由脆**：正则是手写的，换域失效；LLM 兜底那 1 条 miss 还被误分到 faq（答错）——
   **LLM 路由不是万灵药**，1/1 miss 就分错了，说明兜底层也需要测准确率。
4. **延迟含噪声**：本地 1.5B 有冷启动和并发排队抖动，延迟列仅供量级参考，不做精确对比。

## 5. 结论与生产清单

1. **分层混合帕累托占优"全程最强"**：C 比 B 既准又省（0.889/18 vs 0.667/63）——这是核心可复现结论。
2. **架构决定算力的投放效率**（修正版）：架构本身的直接增益有限（+0.112），但它决定"把云端的钱花在哪"，
   让有限预算换最大准确率。架构与算力是乘法关系，不是谁取代谁。
3. **分层 = 按需分配算力**：顶层零成本规则路由分流，贵 orchestrator（DAG/回路/云端）只接该接的。
4. **"全程最强"是把好工具用错地方**：Reflection 该被路由只派给需要迭代的子任务，而非全程开。
5. **worker 失败隔离是硬需求**：子 orchestrator 会非确定性崩溃，调度层必须 try/except 兜住 + 防御缺键。
6. 生产再补：全局 token/步数熔断、每跳统一 trace 接 gateway、规则路由的 A/B 灰度、扩大样本做显著性。

## 6. 与既有实验的关系（叙事闭环）

本实验是 **#06 + #09 + #12 + #18 + #20 的集大成**：
- #20 证明了单层 swarm 的并行/路由机制；
- #21 把"选哪种 orchestrator"上升为顶层决策，用剥离实验量化**分层组合相对单一模式的增益来源**。
- 复现 #12 的 Reflection 负面边界，并给出它的正确用法：**不是全程开，而是只路由给真正需要迭代的子任务**。

---

**面试金句（P7 SA "如何为客户设计 agent 架构"）**:
> "我不会给客户上'全程 Reflection/多 agent 兜底'的重架构。我做过四臂对照加剥离实验：全程 Reflection 烧了 3.5 倍调用、2 倍延迟，准确率反而被分层架构反超。
> 我的做法是分层:顶层零成本规则路由分流——FAQ 走缓存直返、计费走本地小模型、只有复杂技术诊断和合规审核才路由到云端的 DAG 和 Reflection 回路。
> 而且我用剥离实验拆过功劳:架构本身只贡献四分之一的准确率提升，大头是'把难题精准送上云端'。所以我对客户的结论是——**架构不是用来取代算力的，是用来决定算力花在哪、花得值不值的**。同样的调用预算，分层能换来高得多的准确率。"
