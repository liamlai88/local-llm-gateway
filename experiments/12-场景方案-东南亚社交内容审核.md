# 海外场景方案 01：东南亚社交平台内容审核

> **场景**：东南亚社交平台内容安全  
> **对应 Demo**：Demo #1（Dify Workflow + ai-gateway RAG）改造  
> **方案状态**：代码已跑通，可直接 PoC 演示  
> **最后更新**：2026-05-09

---

## 1. 客户画像与痛点

**客户**：东南亚社交平台（印尼/马来西亚市场），日活 500 万，每天新增内容约 50 万条

**四个核心痛点**：

1. **人力成本不可持续**：50 万条/天全靠人工，按每人每天审核 500 条计算，需要 1,000 名审核员，月人力成本 ¥800 万
2. **审核时效性差**：人工审核平均 2 小时后才发现有害内容，此时已传播 10 万次，合规 SLA 无法满足
3. **本地化规则复杂**：东南亚各国有严格的宗教内容规定（伊斯兰教禁忌）、政治敏感词、当地语言俚语，通用模型无法覆盖
4. **误删伤害创作者**：规则过严导致正常内容被删除，创作者流失，影响平台内容生态

**不解决的后果**：
- 违反印尼 GR 71/2019 数据本地化法规，平台面临罚款或封禁风险
- 有害内容扩散损害品牌声誉，广告主撤单
- 1,000 名审核员人力成本随日活线性增长，无法规模化

**为什么不直接用 GPT-4o**：
- 数据主权：印尼/马来西亚要求用户数据不出境，无法调用境外 API
- 规则定制化：本地宗教/政治规则 GPT-4o 不具备，需要私有知识库
- 成本：50 万条/天全量过 GPT-4o，月费用超过 ¥200 万，远超人工成本

## 2. 技术架构

### 核心思路：快慢路径分离

> 90% 内容走规则快路径（<500ms），10% 模糊内容走 LLM 慢路径（<2s），降低 LLM 调用成本 10 倍

### 流量分布

| 层级 | 流量占比 | 每日处理量 | 延迟目标 | 处理方式 |
|---|---|---|---|---|
| 层1 BM25 黑名单 | 70% | 35 万条 | <50ms | 关键词命中直接判定 |
| 层2 RAG 语义匹配 | 20% | 10 万条 | <500ms | 向量搜索匹配审核规则 |
| 层3 LLM 深度判断 | 8% | 4 万条 | <2s | 模型结合上下文推理 |
| 层4 人工复审 | 2% | 1 万条 | <30min | LLM 置信度低或法律敏感 |

### 四层审核流水线

```
用户提交内容
      │
      ▼
┌─────────────────────────────────┐
│  层1：BM25 黑名单关键词匹配      │  <50ms
│  已知违禁词 → 自动拒绝           │
│  无可疑信号 → 自动通过           │
└─────────────┬───────────────────┘
              │ 模糊词汇（如"炸弹"可能是烹饪词）
              ▼
┌─────────────────────────────────┐
│  层2：RAG 语义规则匹配           │  <500ms
│  知识库：平台社区规则 +          │
│         各国法律法规 +           │
│         宗教内容指引             │
│  高置信 → 自动通过/拒绝          │
└─────────────┬───────────────────┘
              │ 置信度低于阈值
              ▼
┌─────────────────────────────────┐
│  层3：LLM 上下文推理             │  <2s
│  模型：Qwen-Turbo（百炼）        │
│  结合用户历史 + 内容语境判断      │
│  高置信 → 结果                   │
└─────────────┬───────────────────┘
              │ 仍不确定 / 涉法律
              ▼
┌─────────────────────────────────┐
│  层4：人工复审队列               │  <30min SLA
│  触发条件：LLM 置信度 < 0.7     │
│           或标记为法律敏感类      │
└─────────────────────────────────┘
```

### 对应已有代码

| 架构层 | 项目代码 | 说明 |
|---|---|---|
| API 入口 | `gateway.py` `/v1/chat` | 统一入口，路由分发 |
| BM25 黑名单 | `rag.py` BM25Search | 已实现，替换知识库即可 |
| RAG 语义匹配 | `rag.py` HybridSearch + Rerank | 已实现，切换为审核规则库 |
| LLM 判断 | `multi_agent.py` Critic 逻辑 | 已实现，调整 prompt 为审核场景 |
| 监控 | `monitoring/` Prometheus + Grafana | 已实现 |

> **方案优势**：代码已跑通，非 PPT 架构，可在客户现场 30 分钟内完成 PoC 演示

## 4. 实施路线图

### PoC 阶段（第 1-2 周）

**目标**：验证端到端工作流链路，让客户看到 Demo

- 部署 ai-gateway + RAG 模块到阿里云新加坡节点
- 导入客户现有审核规则到知识库（100-500 条）
- 跑通：内容输入 → BM25 → RAG → LLM → 结果输出
- **交付物**：可演示的 Demo，含真实客户内容样本的测试报告

### 试点阶段（第 3-8 周）

**目标**：覆盖 10% 真实流量，验证生产可用性

- 灰度放量：5万条/天真实内容经过 AI 审核
- 规则知识库持续补全（根据误判案例迭代）
- **成功标准**：
  - 自动审核率 > 80%（层1+2+3 合计）
  - 误判率（Precision）> 95%
  - 层3 LLM 平均延迟 < 2s P99

### 生产阶段（第 9-20 周）

**目标**：全量上线，稳定运营

- 全量切换，人工复审团队从 1,000 人缩减至 20 人
- 阿里云提供 99.9% SLA 保障
- 客户运营团队负责日常规则库维护（提供管理后台）
- 每季度规则库健康度评估

## 5. 风险与应对

| 风险 | 触发条件 | 应对方案 |
|---|---|---|
| **规则覆盖不全** | 新型违规内容出现，自动审核率下降 | 人工复审案例自动入库扩充规则；设置自动审核率告警（低于 75% 触发） |
| **误删伤害创作者** | Precision 低于 95%，正常内容被删 | 试点阶段 Precision 未达标不全量；提供创作者申诉通道（72h 人工复核） |
| **数据主权合规** | 用户数据出境触发监管处罚 | 全栈部署在阿里云**新加坡/雅加达节点**，满足印尼 GR 71/2019 数据本地化法规，数据全程不出东南亚 |
| **规则知识库老化** | 网络新词/新型规避手法出现 | 每月规则库更新机制；误判案例自动标记，人工审核后补录 |

## 6. 方案亮点总结（面试用）

1. **不是 PPT 架构**：RAG + Multi-Agent + Gateway 代码已跑通，2 周内可 PoC
2. **快慢路径分离**：90% 流量走 <500ms 快路径，LLM 成本降 10 倍
3. **ROI 极强**：月节省 ¥781 万，年节省近亿，AI 系统成本仅 ¥3 万/月
4. **合规原生**：阿里云海外节点，数据不出境，满足东南亚各国法规
5. **可演进**：规则库随业务迭代，准确率持续提升，不锁死在初始版本
