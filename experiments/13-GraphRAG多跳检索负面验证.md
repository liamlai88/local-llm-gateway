# 实验 #13: GraphRAG 多跳检索 —— 抽取质量决定一切

> **核心结论**: 在 10 段小 KB + 5 道多跳题上，朴素 RAG 4/4 (100%) 反超 GraphRAG 3/4 (75%)。
> GraphRAG 不是更聪明的 RAG，它是用「抽取质量」换「检索精度」的赌博。

## 1. 假设与动机

实验 #12 的 Q5 失败暴露了一个问题：RAG 召回错误时 Reflection 无法纠正。
AgentGuide 推荐 GraphRAG 解决多跳问题——通过实体-关系图遍历，跳出"文本块"局限。

**待验证假设**:
- H1: GraphRAG 在多跳关系题上准确率高于朴素 RAG
- H2: GraphRAG 的"可解释性"（路径可视化）能减少幻觉

## 2. 实现

[graphrag.py](../graphrag.py) — 独立模块，不动现有 rag.py / chroma 数据：

```
KB 文档 → LLM 抽三元组 → networkx 建图 (MultiDiGraph)
                                            ↓
query → LLM 抽 query 实体 → 2-hop 子图扩展 → 三元组拼 context → 生成
```

**对照**: 朴素 RAG (百炼 embedding + cosine top-3 + 生成)

## 3. 实验设计

- **KB**: 10 段文档（产品规格 6 段 + 组织结构 4 段），精心设计跨段关系
- **测试集**: 5 道 2-4 跳问题
- **Provider**: 全程 qwen-turbo（消除模型能力影响）

## 4. 知识图谱构建结果

抽取 10 段文档耗时 29s，得 31 节点 / 24 边。

**关键缺陷**（这是后续失败的根因）：
```
原文: "李四是张三的下属"
正确: (李四) --[下属]--> (张三)
实际: (李四) --[是]--> (张三的下属)   ← "张三的下属" 被当成字符串实体
```

**结果**: 张三节点和李四节点**没有边相连**，整个上下级链 `张三→李四→王五→产品` 被打成三个孤岛。

## 5. 5 题对照结果

| Q | Naive RAG | GraphRAG | 备注 |
|---|---|---|---|
| Q1 A100 比 A10 多多少显存 | ✓ 56GB | ⚠️ SSL 错误 | 网络问题，不计入算法对比 |
| Q2 ecs.gn7e vs ecs.gn7i 显存差 | ✓ 56GB | ✓ 56GB | 都能跨段 |
| Q3 套餐 PRO 里 GPU 按量价 | ✓ ¥68 | ✓ ¥68 | 都能跨段 |
| Q4 李四的上级负责什么 GPU | ✓ 无法确定 | ✓ 无法确定 | **答案确实就是无法确定**——张三是 VP 不直接管实例 |
| Q5 张三→下属→下属→产品价 | ✗ 无法确定 | ✗ ¥12000 | 都错，但失败方式截然不同 |

**修正后准确率**:
- Naive RAG: 4/4 = **100%** (Q1 排除)
- GraphRAG: 3/4 = **75%** (Q1 排除)

## 6. 三个核心发现（比正面结果更值钱）

### 6.1 抽取质量是 GraphRAG 的天花板

LLM 抽取倾向于把短语整体作为宾语，破坏图拓扑：

```python
# 期望
(李四, 下属, 张三)    →  张三和李四之间有边

# 实际
(李四, 是, "张三的下属")  →  "张三的下属" 是独立字符串节点
                              张三和李四之间没有边
```

**工业落地要解决的工程问题**:
1. **实体规范化** (entity canonicalization)：建预定义实体表，强制 LLM 复用
2. **关系规范化**：定义闭集合（下属 / 负责 / 使用 / 包含 / 显存 / 价格）
3. **后处理 pass**：识别"X的Y"模式自动拆分成 `(X, Y, _)` 结构
4. **多轮迭代抽取**：第二轮基于第一轮的实体表"找漏关系"

**没做这些之前，GraphRAG 是个理论玩具。**

### 6.2 小 KB + 好 chunk → 朴素 RAG 已经够用

10 段文档全能塞进 top-3 context，LLM 在原文上推理反而比在三元组上更准——因为**三元组丢失了"是的下属"这种带回指的句法细节**。

**GraphRAG 真正的适用门槛**:

| 场景 | 推荐 |
|---|---|
| 小 KB（< 100 段）| ✗ 朴素 RAG + rerank 已够用 |
| 大 KB（> 10k 段）| ✓ 朴素 RAG 召回噪声大，图能精选 |
| 实体同义词多（"A100" / "A100 GPU" / "Ampere A100"）| ✓ 图消歧 |
| 单跳事实题为主 | ✗ 图开销不划算 |
| 多跳关系题为主 | ✓ 前提是抽取质量过关 |
| 高时效性（频繁更新）| ✗ 重建图成本高 |

### 6.3 Q5 揭示新型幻觉：「自信地错」 > 「谦虚地不知道」

Q5 正确答案应该是 ¥35000（张三→李四→王五→ecs.gn7e→¥35000）。

| 模式 | 答案 | 失败模式 |
|---|---|---|
| Naive RAG | "无法确定" | 拒答（**正确的谦虚**）|
| GraphRAG | "¥12000" | **编路径**：李四→ecs.gn7i→套餐 LITE→¥12000 |

**深层原因**: 图结构本身暗示"实体间总有路径"，子图扩展会拉来很多相关三元组，**LLM 看到一堆边就倾向于"凑"出一条答案路径**。

> **GraphRAG 的可解释性是双刃剑**——它能给你"答案路径"，但 LLM 会**为了"显得有路径"而编路径**。
> 这种新型幻觉比朴素 RAG 的"召不回"更危险，因为它给出具体数字 + 看似合理的推理链。

## 7. 工程建议

如果一定要上 GraphRAG，最低成本配置：

1. **闭关系集合 + 实体表**：写在 prompt 里强制约束
2. **同义节点合并**：抽完图跑一遍 entity linking
3. **路径置信度评分**：被遍历到的边给权重，路径越长越衰减
4. **"无路径"显式表达**：让 LLM 看到子图后能输出"图中无支持路径"
5. **混合**：先用 Naive 召回 top-5 chunk，再用图做"关系验证"，而不是用图替代向量检索

## 10. 一句话总结

> **GraphRAG 的天花板由抽取质量决定，而抽取质量是个工程难题。** 在没有实体规范化、关系闭集合、后处理校验的前提下，朴素 RAG + rerank 才是更稳的选择。
> 真正的多跳能力来自 **「检索得对 + 推理得稳」**，不是「换个检索范式」。
