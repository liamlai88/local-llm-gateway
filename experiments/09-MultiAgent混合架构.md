# Multi-Agent 混合架构突破报告

> **核心问题**：单一架构总有局限——纯 LLM Multi-Agent 慢且贵，纯规则 Multi-Agent 快但盲区多。能否把两者组合？  
> **本实验**：实现"规则快路径 + LLM 兜底慢路径"的混合架构，让系统**自动判断**走哪条路。  
> **结论**：**准确率 4/4 等同 Plan-Execute Turbo，平均延迟仅 1/8（1.2s vs 9.8s）。命中题毫秒级，盲区题 LLM 兜底**。  
> **实验时间**：2026.04

---

## 架构演进背景

之前 5 份 Agent 实验揭示了单一架构的局限：

| 架构 | 优势 | 致命弱点 |
|------|------|----------|
| ReAct | 简单 | 多工具任务 25% 天花板 |
| Plan-Execute | 准确率高 | 延迟 5-30s，每次都调多次 LLM |
| 纯规则 Multi-Agent | **0.6ms 极速** | 盲区无法处理 |

**真实生产场景**：80% 的请求是高频简单问题，20% 是低频复杂问题。**用同一种架构处理两类问题都是浪费**。

## 混合架构设计

### 整体流程

```
                  用户问题
                     │
          ┌──────────▼──────────┐
          │  CoordinatorAgent    │ (规则路由)
          │  关键词 + 正则识别    │
          └──────────┬──────────┘
                     │
          ┌──────────▼──────────────────────┐
          │   Worker Agents 并行执行         │
          │   ├── RetrieverAgent (RAG)      │
          │   ├── WeatherAgent              │
          │   ├── CalculatorAgent           │
          │   └── SolutionAgent             │
          └──────────┬──────────────────────┘
                     │
          ┌──────────▼──────────┐
          │   CriticAgent        │ (审计层)
          │   - 必跑的跑了吗？   │
          │   - Solution 是空话？│ ← 关键判断
          │   - KB 有内容但没用？│
          └──────────┬──────────┘
                     │
              passed?│
              ┌──────┴──────┐
              │             │
            YES│           NO│
              │             ▼
              │     ┌─────────────────┐
              │     │ LLMFallbackAgent│  ⭐ 慢路径
              │     │ 用 Qwen-Turbo   │
              │     │ + KB context    │
              │     │ 兜底回答         │
              │     └────────┬────────┘
              │              │
              ▼              ▼
        ┌─────────────────────┐
        │   FinalizerAgent     │ (合成最终答案)
        └──────────────────────┘
```

### 关键创新：Critic 升级为质量裁判

**v1 Critic**（旧）：只检查"必跑的有没有跑"
```python
if needs_calculator:
    check(calculations非空)
```

**v2 Critic**（新）⭐：检查"答案有没有内容"
```python
# 新增 1: Solution 空话检测
if "未识别到" in advice or "建议先补充" in advice:
    fail("SolutionAgent 输出为空话")

# 新增 2: KB 有内容但规则路径未利用
if kb_has_product_content and plan["product"] is None:
    fail("KB 有产品文档但规则未识别 → 需 LLM 兜底")
```

**这是混合架构的灵魂**：Critic 不是只看流程完整性，而是**质量裁判**，决定要不要升级到 LLM 兜底。

## 三个核心洞察

### 洞察 1: 混合架构 = 准确率上限 × 延迟下限

```
单一架构选择题 (旧思维):
  要准 → Plan-Execute Turbo (慢, 9.8s)
  要快 → 纯规则 Multi-Agent (盲区不准)

混合架构 (新思维):
  ✅ 准确率 = Plan-Execute Turbo (4/4)
  ✅ 延迟 = Plan-Execute Turbo / 8 (1.2s 平均)
  
  关键: 80% 请求走快路径，20% 走 LLM 兜底
        加权平均后，性价比远超任何单一架构
```

### 洞察 2: Critic 是混合架构的"路由开关"

混合架构的成败 100% 取决于 Critic 的判断准确度：

```
Critic 太宽松 → 漏判，盲区题被错误判为成功 (假成功)
Critic 太严格 → 误判，简单题被升级到 LLM (浪费)
Critic 精准   → 完美路由 (我们的目标)
```

**升级 Critic 的两个关键检测**：
1. **空话检测**：识别 "未识别到"、"建议先补充" 这类兜底话
2. **资源利用检测**：KB 有内容但规则路径没用上 → 必须升级

### 洞察 3: LLM 兜底必须用强模型

```python
# 错误设计
LLM_Fallback 用 1.5B 本地模型
→ 兜底也答不好 (1.5B 在开放推理上能力不足)

# 正确设计 ⭐
LLM_Fallback 硬编码 Qwen-Turbo
→ 兜底就要用强模型，因为已经触发兜底说明任务复杂
```

**类比**：医院的"专家会诊"必须叫主任医师，不能再叫住院医师。

## 与 Plan-Execute Turbo 的本质区别

表面看两个架构都能 4/4 通过，但**底层经济模型完全不同**：

```
Plan-Execute Turbo (旧):
  每个请求都调 4-6 次 LLM
  无论问题复杂度
  → 成本与请求数线性增长

混合 Multi-Agent (新):
  80% 请求 0 次 LLM 调用
  20% 请求 1 次 LLM 调用
  → 成本与"复杂请求数"线性，与"总请求数"次线性

实际部署 (10 万次/天):
  Plan-Execute Turbo: 10 万 × 4 次 LLM = 40 万次 → ~¥800/天
  混合 Multi-Agent:    8 万 × 0 + 2 万 × 1 = 2 万次 LLM → ~¥40/天
  
  ⭐ 成本节省 95%
```


## 后续突破：模型规模 × 混合架构 完整矩阵 ⭐

针对"混合架构能否让小模型取代大模型"这个问题，做了完整的 3 模型对照实验。

### 实验配置

| 配置 | 命中题路径 | 盲区题兜底模型 |
|------|-----------|----------------|
| Multi-Agent + 1.5B | 规则路径 (0 LLM) | 本地 Qwen2.5-1.5B |
| Multi-Agent + 7B | 规则路径 (0 LLM) | 本地 Qwen2.5-7B (4.9GB 显存) |
| Multi-Agent + Turbo | 规则路径 (0 LLM) | 百炼 Qwen-Turbo (云端) |

### 实验结果

| 配置 | 准确率 | 平均延迟 | 命中题延迟 | 盲区题延迟 |
|------|--------|----------|-----------|-----------|
| Multi-Agent + 1.5B | **4/4 (100%)** ⚠️ | 1385ms | 0-478ms | 1533-3529ms |
| Multi-Agent + 7B | **4/4 (100%)** ✅ | 3378ms | 0-460ms | 5918-7132ms |
| Multi-Agent + Turbo | **4/4 (100%)** ✅ | 1200ms | < 5ms | 2-3s |

### 反直觉发现：1.5B 的"伪通过"陷阱

表面看 1.5B 也是 4/4，但仔细分析盲区题答案：

```
盲区-2: "AI 推理服务, 10 万次请求/天, 选什么 GPU?"

1.5B 答: "推荐 ecs.gn7e-c12g1.3xlarge (A100 80GB)"
        ↑ 答错产品! A100 是训练卡, 推理用 A10 就够
        ↑ 但评判脚本检测到 "推理" 关键词 → 假通过
        ↑ 客户照做会浪费 4 倍预算 (¥35000/月 vs ¥9800/月)

7B 答:  "推荐 ecs.gn7i-c8g1.2xlarge (A10 24GB)"
        ↑ 选型正确 ✅

Turbo 答: 同样 A10 ✅
```

**深层洞察**：
> **"评判 Agent 不能只看关键词通过率，要看选型逻辑是否专业。1.5B 兜底答出关键词但选错产品 → 让客户多花 4 倍钱。生产部署兜底必须 7B 起步。"**

---

### 三个最终结论

**1. 命中题：完全模型无关** ✅

```
1.5B 命中题平均: 240ms
7B   命中题平均: 230ms
Turbo 命中题平均: <5ms (网络往返)
```

差距源于网络/模型加载，不是推理质量。**因为命中题完全不调 LLM**——这是混合架构最大商业价值。

**2. 盲区题：模型规模决定专业度（不是准确率）**

| 模型 | 盲区准确率 | 盲区专业度 | 客户体验 |
|------|------------|------------|----------|
| 1.5B | 100%（关键词）| ⚠️ 选型错 | 差，客户照做亏钱 |
| 7B | 100% | ✅ 选型对 | 好 |
| Turbo | 100% | ✅ 选型对 + 表达专业 | 最好 |

**3. 模型规模 × 范式 完整矩阵（最终版）**

| 范式 | 1.5B | 7B | Turbo |
|------|------|------|------|
| ReAct | 25% | ❌ Ollama 不支持 | 25% |
| Plan-Execute | 75% | 75% | 75% |
| **Multi-Agent 混合** | **100%** ⚠️ | **100%** ✅ | **100%** ✅ |

**关键洞察**：
- **同范式跨模型**：1.5B → 7B → Turbo，准确率回报递减
- **同模型跨范式**：ReAct → Plan-Execute → Multi-Agent，准确率从 25% → 100%
- **架构创新 > 模型升级**
